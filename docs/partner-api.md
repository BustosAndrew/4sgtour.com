# Partner API — latest trips

Read-only feed of recently published trips, authenticated with an API key
issued from **Admin → API Access**. Built for Tiger Booking
(`tigerbooking.com`), but the key mechanism is generic.

This is the internal reference. The version written for the partner lives in
[partner-api-instructions.md](partner-api-instructions.md).

## How keys work

- Format `4sg_live_<43 chars base64url>`, from `randomBytes(32)`.
- Only `sha256(key)` is stored. `key_prefix` (first 17 characters) exists purely
  so an admin can tell two keys apart in the list — the secret is unrecoverable
  after the create response.
- Revoking is a soft delete (`revoked_at`), so `last_used_at` and the audit
  trail survive. It takes effect on the next request; nothing is cached.
- `last_used_at` is written at most once a minute per key, so a busy partner
  doesn't generate a write per request.

## Authorization boundaries

- The admin page and both admin routes re-check `getUserType() === 'admin'`
  server-side and use the **cookie-bound** client, so RLS is a second gate.
  `key_hash` is never selected into anything that reaches a browser.
- `authenticateApiKey()` uses the **service-role** client. It has to: the
  caller is a machine with no Supabase session, so RLS would hide every row
  from it. This is the same exception the cron routes make.
- The partner endpoint also queries with the service-role client, having
  already established the caller from their key.

## Custom trips are opt-in, behind two gates

A trip with `is_custom = true` is generated by the admin custom-booking flow
for one named customer, is attached to that customer's inquiry, and is hidden
from every public listing. Exposing one leaks a private booking, so reaching
it needs both:

1. **`api_keys.allow_custom_trips`** — granted per key by an admin, on the
   create form or the toggle in the key list. Defaults to false.
2. **`?include_custom=true`** — the partner opts in per request.

Without the parameter the endpoint filters `.neq('is_custom', true)`, matching
the public pages exactly. With the parameter but without the grant it returns
**403 `custom_trips_not_permitted`** rather than silently falling back — a
partner who believes they are receiving custom trips should find out on the
first call, not from a gap in their catalogue. Every trip in the response
carries `is_custom` so a caller can tell the two kinds apart either way.

Withdrawing the grant (`PATCH /api/admin/api-keys/[id]`) takes effect on the
next request, same as revoking.

## Migration status

Both `scripts/054_add_api_keys.sql` and
`scripts/055_add_allow_custom_trips_to_api_keys.sql` were applied by hand in
the Supabase SQL editor on **2026-08-15**, so the schema is live and the code
can ship.

They ran against the shared Supabase project, which means the `api_keys` table
is visible to all three deployments even though only this repo has the code to
use it. That is also why a key issued here works against `.de` and `.at` if
those ever gain the endpoint — see the note in CLAUDE.md.

Any future change here is a new numbered script, applied the same way, plus a
matching edit to `lib/types/database.ts`. A migration and the code that needs
it deploy separately, so run the SQL first.
